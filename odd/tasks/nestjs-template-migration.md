# NestJS template migration

## Objective

Rebuild `ventylab-server` so it looks as if it had been generated from `template-backend-nestjs` from day one: NestJS 11, hexagonal/DDD features (`domain`, `application`, `infrastructure`, `presentation`), the template code style, envelope, errors, i18n, config, guards and tooling.

## Problem and why

The current server is Express 4 with heterogeneous modules, inline Prisma access in controllers, five different response shapes and ad-hoc auth. The author wants the backend aligned with the template architecture; the frontend (`ventilab-web`) will be migrated separately to its own template.

## Decisions (accepted)

- **ORM:** keep Prisma (user decision). Repositories live under `infrastructure/persistence/prisma/{mappers,repositories}/*-prisma.repository.ts`. `PrismaService` + `PrismaTransactionManager` replace the Drizzle module. Existing table and column names are not renamed (no data migration on Neon).
- **HTTP contract:** adopt the template envelope `{ success, message, data, code, timestamp, traceId, pagination }` on every route and the template error filter (user decision: frontend adapts separately). No per-route backward compatibility.
- **Routes:** keep resource paths under `api/`, kebab-case. Drop legacy duplicate mounts (`/auth`, `/progress`, `/admin`) and the `/api/api` rewrite. Teacher-student admin endpoints move from `/api` to `/api/teacher-students`.
- **Code style:** template style, EXCEPT every `src/**/*.ts` file starts with the authorship header (Funcionalidad, Descripción, Versión, Autor, Proyecto, Tesis, Institución, Contacto). Reversed on 2026-10-04 per the author's shared-layer prompt and the project CLAUDE.md.
- **Authorization:** template permission model (`resource:action` catalog + `PermissionsGuard`). The existing `UserRole` enum is mapped to permissions in code; `SUPERUSER` behaves as template `root`. No schema change for roles.
- **Security fixes inherited from template patterns:** register no longer accepts `role` from the body; the NextAuth bridge requires a shared secret.
- **Audit and error logs:** template `audit_logs` and `error_logs` tables are added to `prisma/schema.prisma`; the migration SQL is generated but **not applied** to Neon (the author applies it).
- **Git:** no commits, branches or pushes by the agent (project rule overrides ODD work-unit commits). Recovery relies on this document and the Engram mirror.
- **Preserved as-is:** `prisma/` (incl. 15 local, gitignored migrations), `.env*`, `scripts/` (thesis evidence; only their imports are updated), `docs/json-specs/`, `contracts/` content reused by simulation, `__deferred_tests__/`, `audit-output/`.

## Scope

In: everything under `src/`, root tooling (package.json, tsconfig, nest-cli, eslint, editorconfig, husky/lint-staged), agent docs (`CLAUDE.md`, `AGENTS.md`, `.claude/skills/` adapted to Prisma), `prisma/schema.prisma` additions, `scripts/` import paths, `AI_CONTEXT.md` regeneration.

Out: `ventilab-web`, applying DB migrations, deploying, data changes.

## Constraints

- Verification: `npx tsc --noEmit` must be green (server baseline is green). No `npm run <script>`, no build.
- Explore the old implementation through `git show main:<path>` after cleanup.
- Realtime contract (socket events `authenticate`, `authenticated`, `auth_error`, `ventilator:data|alarm|reserved|released`; MQTT topics) keeps its event names; payload shapes may follow the template where it applies.

## Acceptance criteria

- Every feature has `domain/`, `application/`, `infrastructure/`, `presentation/` and a `{feature}.module.ts`, following template naming (`*.usecase.ts`, `*-prisma.repository.ts`, `*.dto.ts`, `*.entity.ts`).
- All responses go through `APIResponseBuilder`; all errors go through the template `HttpExceptionFilter` with domain error codes translated in `src/i18n/{en,es}`.
- Every legacy endpoint has an equivalent route (paths per the decisions above).
- `npx tsc --noEmit` reports 0 errors.
