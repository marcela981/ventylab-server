# Identity features: auth, users, groups

## Objective
Bring the identity features (auth, users, groups) to the requirements of the author's identity prompt, inside the existing NestJS hexagonal architecture, without breaking token format, refresh flow or existing HTTP contracts.

## Decisions (confirmed by the author, 2026-10-05)
1. Structure: NestJS layers per feature; the "index.ts public API" is a facade exported by the module (`UsersFacade`, `GroupsFacade`). Only auth/users/groups consumers migrate to the facades; other features importing users/groups internals are recorded as debt.
2. `SUPERUSER` is folded into `ADMIN` (enum recreated; SUPERUSER ids snapshotted in `audit_logs`); guard bypass and `register/superuser` removed; ADMIN gets the full catalog.
3. Refresh revocation without changing token format: `users.refreshTokensRevokedAt`; `/refresh` rejects tokens whose `iat` is older.
4. Memberships are additive: new `memberRole` (`LEADER|MEMBER`), backfilled from `simulatorLeaderId`, which stays synced in the same transaction; legacy `role` column kept; `id` PK kept (`@@unique([groupId,userId])` already exists).
5. `Group.type` (default STUDENT) inferred from members; `group_supervisions` created empty (populated from the tree only with the author's approval); `parentGroupId`/`depth` and `teacher_students` untouched.
6. New routes: `POST api/auth/google`, `GET api/users`, `PATCH api/users/:id/role`, `PATCH api/users/:id/status`, `api/groups/:id/supervisions`, `GET api/groups/mine`; `api/admin/users/:id/role` stays as alias.
7. "One student group per student" and "one leader per group" are enforced in services inside a transaction with `pg_advisory_xact_lock` (no partial indexes).
8. `google-auth-library` is installed (author approved).
9. Pre-existing data conflicts (students in several groups, role mismatches) are not resolved by the migration; `verification.sql` lists them for the author.

## Constraints
- No git writes; no `npm run`; no DB connection; no `prisma migrate dev/deploy/db push`; SQL generated offline and applied only by the author.
- No `.env*` reads/writes; no frontend changes; no user or student data deletion.
- Schema changes additive or with explicit lossless data migration.
- Mandatory authorship header on every new or modified `.ts` file.
